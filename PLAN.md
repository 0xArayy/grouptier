# GroupTier — Template Search Improvements (Tags + Option Search)

Generated by /autoplan on 2026-05-30
Branch: main
Scope: Add `tags` metadata to curated templates and extend public-poll search to match option text.

## Goal

Users searching in PresetsStep currently match only template **names** for user-published polls.
For curated `public_templates`, options are already matched client-side but tags are absent.
Two improvements:

1. **Tags on curated templates** — add a `tags TEXT[]` column to `public_templates` so admins
   can attach keyword aliases (e.g. "Лучшие RPG" → tags: ["rpg", "ролевые", "фэнтези"]).
   Frontend includes tags in the search filter.

2. **Option-text search for user-published polls** — `GET /api/public-polls?q=` currently runs
   `name ILIKE $1` only. Extend to also match option text inside the `options JSONB` column.

## Current State

| Source | Search fields | Where filtered |
|--------|--------------|----------------|
| `public_templates` | name, options | Client-side (PresetsStep.tsx L96-98) |
| `saved_polls` (public) | name only | Server-side ILIKE |

### What already works
- PresetsStep line 97-98: `t.options.some(o => o.toLowerCase().includes(q))` — option search for curated templates ✅
- GET /api/templates — no query param; returns all templates cached in-process (~20-50 rows) ✅ (small set, client filter is fine)
- GET /api/public-polls — ILIKE name only; can grow to thousands of rows ⚠️

## Architecture

```
public_templates (DB)
  ├── id, emoji, name, options JSONB, author, official, category, created_at
  └── tags TEXT[]  ← NEW (migration S1)

saved_polls (DB)
  ├── id, name, options JSONB, categories, uses_count, is_public ...
  └── option search via jsonb_array_elements_text() ← server query change (S3)

GET /api/templates
  └── FULL_QUERY adds t.tags ← S2 (already cached, client filters)

GET /api/public-polls?q=
  └── WHERE name ILIKE $1 OR EXISTS(jsonb option match) ← S3

PresetsStep.tsx
  └── tag match: t.tags?.some(tag => ...) ← S4 (one-liner addition)
```

## Decisions

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| D1 | Tags source | Admin-assigned explicit tags | Most reliable; AI-generated tags risk incorrect metadata |
| D2 | Template search approach | Client-side filter (keep current) | Curated set is small (~20-50); no server round-trip needed |
| D3 | Public-poll option search | Server-side via jsonb_array_elements_text() | User polls can reach thousands; client-side not feasible |
| D4 | Option search SQL | `EXISTS (SELECT 1 FROM jsonb_array_elements_text(options) elem WHERE elem ILIKE $1)` | Precise per-element match; avoids false positives from `options::text` substring match |
| D5 | Tags seed | Manual SQL UPDATE with curated tags per template | Small set; explicit, reviewable, correct |
| D6 | No GIN index on options for user polls | Skip for now | Full-table scan on <1k rows is <10ms; add if catalog grows to 10k+ |

### S3 — Server: add option-text search to `GET /api/public-polls`

- **Priority:** P1
- **Files:** `server/src/routes/publicPolls.ts`
- Change the search branch from:
  ```sql
  AND name ILIKE $1
  ```
  to:
  ```sql
  AND (
    name ILIKE $1
    OR (
      jsonb_typeof(options) = 'array'
      AND EXISTS (
        SELECT 1 FROM jsonb_array_elements_text(options) elem
        WHERE elem ILIKE $1
      )
    )
  )
  ```
  (⚠️ CEO flag: `jsonb_typeof` guard is required — not optional. Without it, a single malformed `options` value breaks the entire search endpoint.)
- `$1` stays `%${q}%` — no other param changes.
- Also add `matched_option?: string` to the SELECT — returns the first option text that matched via JSONB search, or NULL (see S3b below).
- **Tests:**
  - `q=` matches by name (existing test passes unchanged)
  - `q=` matches by option text when name doesn't match
  - `q=` matches nothing → empty items array
  - `q=` option match → `matched_option` populated in response

### S3b — Server + Frontend: matched option indicator

- **Priority:** P2 (taste decision T1 — see final gate)
- **Files:** `server/src/routes/publicPolls.ts`, `frontend/src/components/create-poll/PresetsStep.tsx`, `frontend/src/api/client.ts`
- **Problem (design subagent flag):** When S3 option-text search returns a poll, the card shows only name + meta. Users can't tell why it appeared if the name doesn't match the query — silent confusion.
- **Fix — server:** Use `LEFT JOIN LATERAL` to materialize the match ONCE (avoids triple JSONB scan from CASE+EXISTS+subquery pattern):
  ```sql
  -- In the q-branch SELECT, extend SELECT and add join:
  SELECT ...existing fields...,
         mo.elem AS matched_option
  FROM saved_polls
  LEFT JOIN LATERAL (
    SELECT elem
    FROM jsonb_array_elements_text(options) elem
    WHERE elem ILIKE $1
    LIMIT 1
  ) mo ON true
  WHERE is_public = true
    AND (
      name ILIKE $1
      OR (jsonb_typeof(options) = 'array' AND mo.elem IS NOT NULL)
    )
  ```
  The LATERAL join scans JSONB ONCE per row; result reused in both WHERE and SELECT. When `q` is absent, omit the LATERAL join and `matched_option` field (two separate query strings as currently structured).
- **Fix — types:** Add `matched_option?: string | null` to `PublicPoll` interface (must be updated atomically with server — same PR).
- **Fix — frontend:** In `PresetsStep.tsx` poll card (lines 266-300), add after `.cardMeta`:
  ```tsx
  {p.matched_option && q && !p.name.toLowerCase().includes(q) && (
    <div className={styles.cardMatchedOption}>Содержит: «{p.matched_option}»</div>
  )}
  ```
  Add `.cardMatchedOption` CSS: `font-size: 11px; color: var(--tg-theme-hint-color); margin-top: 2px;`

### S4 — Frontend: include tags in PresetsStep template filter

- **Priority:** P2 (depends on S2)
- **Files:** `frontend/src/components/create-poll/PresetsStep.tsx`
- Current filter (line 97):
  ```ts
  return t.name.toLowerCase().includes(q) || t.options.some((o) => o.toLowerCase().includes(q));
  ```
- Change to:
  ```ts
  return (
    t.name.toLowerCase().includes(q) ||
    t.options.some((o) => o.toLowerCase().includes(q)) ||
    (t.tags ?? []).some((tag) => tag.toLowerCase().includes(q))
  );
  ```
- Update `PublicTemplate` type in `frontend/src/api/client.ts` to add `tags?: string[]` (optional — old cached responses may not have this field)
