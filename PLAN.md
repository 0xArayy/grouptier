# GroupTier — WebSocket Live Results

Generated by /plan-eng-review on 2026-05-29
Branch: main
Scope: Replace 3s REST polling on the live results screen with a WebSocket push + auto-reconnect.

## Goal

The live results screen in App.tsx currently calls `GET /api/sessions/:id` every 3 seconds via `setInterval`. Every connected user generates continuous REST traffic, and updates feel jerky (up to 3s stale). Replace with a WebSocket push from the server so updates arrive the moment another user submits their ranking or the host closes the session.

## Architecture

```
┌────────────────────────────────────────────────────────────┐
│                        Server                              │
│                                                            │
│  POST /results  ─► sessionEvents.emitSession(id) ─────┐   │
│  POST /close    ─►           ↑                         │   │
│                                                        ▼   │
│  WS /ws/sessions/:id ──────────────── listener cb     │   │
│       │                            query DB (4 parallel)   │
│       │                            push SessionData payload│
│       └── on WS close: offSession(id, cb)                  │
└────────────────────────────────────────────────────────────┘
         ↑ WebSocket
┌────────────────────────────────────────────────────────────┐
│                       Frontend (App.tsx)                    │
│                                                            │
│  startLiveWs(sessionId)                                    │
│    new WebSocket('/ws/sessions/:id?initData=...')          │
│    onmessage → setSession(data)                            │
│    onclose → scheduleReconnect(backoff)                    │
│    cleanup: ws.close() + clearTimeout on unmount           │
└────────────────────────────────────────────────────────────┘
```

**No Redis. No PG LISTEN/NOTIFY.** In-process Node.js EventEmitter (D1). Clean abstraction boundary: `sessionEvents.ts` exports `emitSession`, `onSession`, `offSession` — callers never import EventEmitter directly. Swapping to Redis or pg NOTIFY later means rewriting one file.

## Decisions

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| D1 | Event mechanism | In-process EventEmitter | Zero infra, single server. Abstraction layer ready to swap. |
| D2 | WS auth | initData as URL query param | Browser WebSocket API can't send custom headers. Matches existing auth model. |
| D3 | Event coverage | Emit from /results AND /close | Missing close-event = users never see session end in real time. |
| D4 | Resilience | Pure WS + exponential backoff reconnect | One code path; polling fallback creates race conditions. Reconnect pushes fresh snapshot on reopen — catches close events missed during backoff. |
| D5 | Scope | Live results only; defer collecting-phase polling | CreatePoll.tsx polling is a different event source, lower latency-sensitivity. |
| T3 | Log safety | Fastify logger redaction for WS URL query params | initData in access logs is a real credential exposure. 2-line fix. |
| T4 | Connection cap | Accept as known risk at current scale | Telegram groups have practical limits (20–200 members). Document; add cap in follow-up if needed. |

## Implementation Tasks

### W1 — `server/src/lib/sessionEvents.ts` (NEW)
- **Priority:** P1
- **Files:** `server/src/lib/sessionEvents.ts`
- Singleton typed EventEmitter. Call `setMaxListeners(0)` on creation (prevents Node.js MaxListeners warning when >10 viewers connect to one session).
- Exports three functions, never the raw EventEmitter:
  ```ts
  export function emitSession(id: string): void
  export function onSession(id: string, cb: () => void): void
  export function offSession(id: string, cb: () => void): void
  ```
- **Test:** emit fires listener; emit with no listeners = no-op.

### W2 — `server/src/lib/sessions.ts` — extract `buildSessionPayload`
- **Priority:** P1 (required by W3)
- **Files:** `server/src/routes/sessions.ts` (or new `server/src/lib/sessionPayload.ts`)
- Extract the 4-parallel-query logic from `GET /api/sessions/:id` into a shared helper:
  ```ts
  export async function buildSessionPayload(id: string, userId?: number): Promise<SessionData>
  ```
  **Important:** this helper does NOT call the voter registration INSERT (`session_voters`). That side-effect stays ONLY in the GET handler. The WS push path calls `buildSessionPayload` without voter registration to avoid inflating voter counts on every push.
- **Test:** Covered implicitly by GET endpoint tests; add one direct unit test asserting it returns the correct shape.

### W3 — `server/src/routes/ws.ts` (NEW)
- **Priority:** P1
- **Files:** `server/src/routes/ws.ts`
- Route: `GET /ws/sessions/:id` (WebSocket upgrade via `@fastify/websocket`)
- Auth: read `initData` from `request.query.initData` (existing middleware updated in W5)
- On connect:
  1. Register EventEmitter listener first (`onSession(id, listener)`)
  2. Then push initial snapshot (`buildSessionPayload(id, userId)`) so client is immediately up to date
  3. Order matters: if snapshot is pushed before listener registration, a result submitted during the query window is silently dropped
- On event fire: call `buildSessionPayload(id)`, push JSON to socket. DB error: close WS gracefully (no server crash).
- On WS close: `offSession(id, listener)` — required to prevent listener leak
- Rate limit: HTTP upgrade request inherits existing `@fastify/rate-limit` (100 req/min per IP). No additional WS-specific limit.
- Known limitation: no hard cap on concurrent WS connections per session. Telegram group size (~200 max) is the practical limit. Add a Map-tracked cap if sessions ever get larger.
- **Tests:**
  - Valid initData → 101 Switching Protocols
  - Invalid initData → 401 (WS never opens)
  - Listener registered before initial snapshot push (order verified in test via mock ordering)
  - `emitSession(id)` fires → WS receives updated payload
  - DB error in push → WS closes gracefully, server does not crash
  - WS close event → `offSession` called (verify via mock)

### W7 — `frontend/src/api/client.ts` — WS helper
- **Priority:** P1
- **Files:** `frontend/src/api/client.ts`
- Add `connectSessionWs(sessionId, onData, onClose)` helper:
  ```ts
  export function connectSessionWs(
    sessionId: string,
    onData: (session: SessionData) => void,
    onClose: () => void,
  ): WebSocket {
    const initData = getInitData();
    const protocol = window.location.protocol === 'https:' ? 'wss:' : 'ws:';
    const url = `${protocol}//${window.location.host}/ws/sessions/${sessionId}?initData=${encodeURIComponent(initData)}`;
    const ws = new WebSocket(url);
    ws.onmessage = (e) => onData(JSON.parse(e.data));
    ws.onclose = onClose;
    return ws;
  }
  ```
- **Test:** Mock WebSocket — onmessage triggers onData with parsed payload; onclose triggers onClose.

### W8 — `frontend/src/App.tsx` — replace polling with WS + reconnect
- **Priority:** P1
- **Files:** `frontend/src/App.tsx`
- Remove: `pollRef`, `setInterval` in `startPolling`, `clearInterval` calls.
- Replace `startPolling(sid)` with `startLiveWs(sid)`:
  ```ts
  function startLiveWs(sid: string) {
    let reconnectTimeout: ReturnType<typeof setTimeout> | null = null;
    let backoff = 1000;
    let ws: WebSocket | null = null;
    let stopped = false;

    function connect() {
      ws = connectSessionWs(sid, (data) => {
        setSession(data);
        if (data.status === 'closed') stop();
      }, () => {
        if (stopped) return;
        reconnectTimeout = setTimeout(() => {
          backoff = Math.min(backoff * 2, 30000);
          connect();
        }, backoff);
      });
    }

    function stop() {
      stopped = true;
      if (reconnectTimeout) clearTimeout(reconnectTimeout);
      ws?.close();
    }

    connect();
    return stop; // returned for cleanup
  }
  ```
- Call `startLiveWs(sessionId)` in the same two places `startPolling` was called.
- Store the returned `stop` fn in a ref; call it in the `useEffect` cleanup.
- **Tests:**
  - WS message event updates session state (mock WebSocket)
  - WS close triggers reconnect schedule
  - `stop()` called on unmount cancels reconnect timeout and closes socket

## Data Flow — Session Payload (pushed via WS)

Same shape as `GET /api/sessions/:id` response (reuses `buildSessionPayload`):
```ts
{
  id, name, status,       // status:'closed' tells frontend to stop WS
  options,
  voter_count,
  result_count,
  borda_ranking,          // updated Borda scores — what users watch live
  my_result,              // null in WS push (userId not tracked per-connection)
  share_url,
}
```

`my_result` will be `null` in WS pushes since the server doesn't associate userId with WS connections. The frontend already has `my_result` from the initial submit response — no regression.

## Failure Modes

| Codepath | Failure | Test? | Error handling? | User impact |
|----------|---------|-------|-----------------|-------------|
| WS connect | Auth failure (bad initData) | ✅ | 401, WS never opens | Transparent (WS silently fails; reconnect retries forever) |
| WS push | DB error during payload query | Gap | Catch + ws.close() | User reconnects; gets fresh snapshot on open |
| WS listener | emitter.off() not called on close | ✅ (W3 test) | offSession in onclose | Memory leak — prevented by test |
| Reconnect | Server restarts during backoff | — | Next reconnect gets fresh snapshot | Up to 30s delay; then normal |
| Reconnect | Session closed during backoff | — | Fresh snapshot on reconnect includes status='closed' | Client exits WS loop when it reconnects |

**Critical gaps:** None — every failure mode has either a test, error handling, or the behavior is acceptable.
