## Goal

Deliver four concrete improvements:

1. **[land-public-templates]** — Merge `feat/public-poll-design` (14 commits, already /reviewed) to main. Public template catalog + HOT/OFFICIAL browser in PresetsStep, publish/unpublish flow, MyPollsStep redesign.
2. **[templates-cache-control]** — Add 30-second in-process Map cache to `GET /api/templates` in `templates.ts`. Railway has no CDN; `s-maxage` does nothing without one. Module-level `let cache: {data: unknown, ts: number} | null` with 30s TTL — 2 lines of code, guaranteed DB hit reduction.
3. **[templates-pagination]** — Cursor-based `?after=<uuid>` pagination for `GET /api/templates`. Currently returns all templates (fine at 9 seeds, breaks at scale).
4. **[canvas-worker]** — Offload `canvas.toBuffer('image/png')` in `server/src/bot/imageCard.ts` to a `piscina` worker pool. Blocks the event loop for ~5–30 ms per card; at multi-group scale this will queue requests.

**Not in scope (Sprint 3):**
- `[websocket]` — Replace REST polling with WebSocket + Redis pub/sub. Infra change (Redis dependency, connection management, Telegram Mini App upgrade path). Week-2 work.

### 0C-bis. Implementation Alternatives

**APPROACH A: Minimal (as planned)**
  Summary: Add Cache-Control header, cursor pagination, piscina worker pool. No new infrastructure beyond piscina.
  Effort: S
  Risk: Low–Med (piscina+ESM footgun)
  Pros: Small diff, deployable in one sprint, no new services
  Cons: In-process cache more effective than HTTP cache without CDN; pagination adds complexity for current <20 template count

**APPROACH B: In-process caching instead of HTTP cache**
  Summary: Replace HTTP Cache-Control with a simple module-level Map cache with 30s TTL for GET /api/templates. Skip pagination for now (defer to Sprint 3 when template count warrants it).
  Effort: S
  Risk: Low
  Pros: Works without CDN, guaranteed DB hit reduction, no pagination complexity at 9-template scale
  Cons: Cache doesn't survive server restart; slightly more code than a header

**APPROACH C: HTTP cache + in-process fallback**
  Summary: Add both `max-age=60` header (for within-session browser cache) AND 30s in-process Map cache. Pagination deferred.
  Effort: S
  Risk: Low
  Pros: Defense-in-depth caching; handles both browser and server-side hits; best real-world perf
  Cons: Two caching mechanisms to explain; marginal benefit over B alone

**RECOMMENDATION:** Approach B (in-process cache, defer pagination). Reason: at 9-template count, pagination adds implementation complexity without user benefit. The in-process cache is 2 lines of code and always works. Approach C is almost as good but slightly over-engineered.
